# 通知投递与恢复

## 两套待发状态

全局轮询汇总队列与勿扰计数是两套状态，均保存在 `cursor_dir/notification_outbox.db`，默认 `data/cursor/notification_outbox.db`。使用 SQLite 事务与 FULL 同步，数据库文件权限为 0600。Docker 应持久挂载数据目录；删除或替换该目录也会删除待发状态。

- **全局轮询汇总队列**保存事件数据、来源和日志条目，不序列化运行时 handler。重启后恢复，由真实事件处理器重新构建通知。每批最多 500 条，失败后保持同一批次的成员和顺序，至少间隔 60 秒重试。新增事件等待下一批，成功确认不会清除同时入队的新事件。
- **勿扰外部计数**按实际勿扰时段分别保存。主日志事件仍从原数据库查询，外部库、Docker、SSH journal 等事件保存计数。时段结束后将两者固化成待发汇总，发送前提交状态；全部渠道失败或抛异常时保留该正文和时段，不推进完成游标。重启后恢复，最早 60 秒后重试。若已进入下一个勿扰时段，则等勿扰结束再继续处理，旧批次与新时段不混在一起。

全局轮询批次转交勿扰计数时，先持久化接收回执，再确认原队列。回执保存七天，避免队列删除失败、进程重启或跨过勿扰结束时间时重复计数或直接重发。

取消勾选事件后，尚未开始发送的全局队列记录不再投递。关闭全局轮询汇总仍会处理此前已入队的批次。关闭勿扰会在同一事务中取消其待发计数、汇总和接收回执；原全局队列中尚未确认删除的事件会重新真实投递，发送失败继续保留。已固化的失败汇总在勿扰保持开启时按原批次继续处理。

如果进程在“保存关闭配置”与“热加载清理”之间退出，下次启动时也会清理残留勿扰状态。关闭勿扰时，发送路径不会再因旧回执而短路成功。

## 成功与失败

任一渠道成功或通知器确认重复已处理，就确认整个批次。全部渠道失败才重试，不整批重推部分失败的通知，否则会向已经收到的渠道重复发送。

勿扰汇总的“本次汇总推送：成功 / 失败”状态消息是辅助提示：仅在正文已确认后发送，其失败会记录推送历史，不回滚正文确认，也不会重新推送正文。

入队写盘失败以 `OutboxWriteError` 向上游报告。主日志不因达到普通批次的三次异常上限而丢弃未入队记录；备份、任务计划、相册、影视登录、SSH 和 Docker 轮询也会保留相应水位或重放机会。音乐/影视专门静默汇总仍保留各自已有的批次持久化，不套入全局轮询汇总。

## 保证边界

这能恢复已观察且已成功提交到本地数据库的待发事件，不会补发应用停机期间尚未观察的所有历史记录。渠道长期不可用时，待发数据会持续占用磁盘空间；应保留并关注数据目录容量。

投递仍可能重复：如果远端已接收，进程在本地完成确认前崩溃，恢复后可能再次发送。HTTP 推送与本地 SQLite 之间无法共同提交事务，不能承诺严格只发送一次。要针对部分失败渠道单独重试，需要另外引入每个目标的投递状态和幂等约定，本轮保留现有的部分成功策略。

收藏和歌单在曲目读取事务结束后分别读取，能缩短读锁占用。它们不保证与曲目快照同时发生；时间差取决于轮询间隔、记录写入及推送耗时，不能限定为毫秒级。
