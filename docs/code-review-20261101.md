## 已修复的问题

1. **音乐推送失败被当成成功**：`EventProcessor._handle_simple_notification` 丢弃真实 `NotificationResult`，导致音乐汇总被清空、收藏和歌单游标推进。现在把结果返回轮询器；全部渠道失败时，音乐汇总保留并按既有间隔重试，即时音乐事件不推进失败记录的游标。
2. **重启丢弃已观察的音乐汇总**：启动循环和基线初始化均清空 `music_pending`。现在保留已落盘批次，只对齐离线期间的新记录；停止轮询时不另外发起网络请求。
3. **仅勾选音乐移出监控时漏报**：新增 ID 只在入库事件启用时加入有效曲目快照。现在移出监控也持续追踪新 ID，不额外发送入库通知。
4. **并发入库可能被 MAX(id) 水位跳过**：扫描新曲与读取最高 ID 不在同一快照。现在曲库扫描与水位更新使用只读事务，通知投递前释放事务，避免慢渠道延长数据库读锁。
5. **SSH 提醒停止后仍可能发送或重新调度**：`stop()` 仅取消 Timer，已进入执行的回调可以继续工作并在 finally 中创建新 Timer。增加停止状态检查，阻止过期回调与重新调度，持久化会话仍可在 start 时恢复。
6. **容器内 systemctl 探测失败被误判为 SSH 关闭**：命令存在但无法连接 systemd 时也返回 False，清空提醒。现在只有明确 inactive/failed/deactivating 才确认关闭；无法探测返回未知，并继续依据 journal 服务事件维护计时。
7. **旧 SSH 关闭配置在页面显示为开启**：`0 or 30` 把旧版关闭值改成 30，GET 返回的事件列表错误加入 SSH_OPEN_TIMEOUT。现在保留零值参与迁移，与运行时规则一致；GET 不改写文件。
8. **CPU 同名进程聚合选错 PID**：首个进程没有记录峰值，随后较低占用的进程可覆盖其 PID。现在保留实际占用最高进程的 PID，总占用仍按应用累加。
9. **长标题音乐汇总的末尾可能被渠道截断**：双阶段各六条长标题预览的复现正文为 2207 字节，超过企业微信应用通知器的 2000 字节截断预算。改为各四条，给标题、时间与说明留空间；完整计数不变，省略数量相应增加。
